# Invariants and failure matrix

Phase 0 specifications with scoped Phase 1–7 evidence, 2026-11-04. F1–F10 specified bounded variants now have executed Phase6 evidence; actual layers and unsupported modalities appear in milestone overlays below. This is not formal or universal certification. Logical statements are design obligations, not formal verification results. The [protocol](PROTOCOL_SPEC.md) defines transitions; the [evidence register](ENGINEERING_EVIDENCE_REGISTER.md) maps claims and narrow executed checks to these IDs.

## Failure model and notation

Let S(x) be the committed server record for ID x, or absent; R(m) the committed terminal receipt for mutation ID m; E(m) its canonical immutable envelope. `rev(S)` is the numeric value of its decimal revision string. `Q(c,x)` denotes a queued/unknown mutation for client c and record x. Clean records, drafts and receipt history are separate local objects.

Supported failure model: lost, duplicated, delayed or reordered HTTP requests/responses; request timeout; Node/application process termination and restart against the same PostgreSQL data; interruption before/after database commit; ordinary browser process restart with the same persistent non-private profile; interrupted local transactions; concurrent distinct clients; extended disconnection with retained state. Tests may inject storage transaction aborts to verify safe failure behavior.

Dependencies: correct PostgreSQL/IndexedDB implementations and transaction use, working persistent storage, database settings appropriate to acknowledged commits, no administrative pruning/reset/rollback restoration, single active controller per client profile, stable protocol version, and honest local demo clients. Progress additionally requires repeated reachable sync opportunities and user decisions. Unsupported: physical storage destruction/corruption, browser eviction/clearing, private-profile lifetime, OS/power-loss guarantees, malicious peers, authorization/security correctness, competing same-profile tabs, distributed database failover, backup restoration, or perpetual network outage. Unsupported cases must not be described as covered by process-restart evidence.

## Stable invariant registry

### INV-ACK-01 — acknowledged server effects persist within the failure model

**Statement:** A valid committed outcome returned for m implies R(m) and its effect committed together. Later supported HTTP/application-process failures do not undo that commit. A later valid mutation may supersede the record; current state need not equal the historical receipt.

**Scope/dependencies:** Same retained PostgreSQL database and sound transaction/durability configuration. Supports application crashes and lost responses; excludes physical loss and administrative restore/reset. **Transitions/failure behavior:** Server commit precedes response; replay after restart returns R(m), even after later revisions. **Planned checks:** F1, F6, T-REPLAY-ADVANCED (Phases 1/3). **Evidence boundary:** Durable queries plus a real Node restart support retention in that environment; a mock success response or one successful GET does not establish persistence under every failure or a historical audit of all record values.

### INV-ATOMIC-01 — effect and receipt are inseparable

**Statement:** For every committed `committed` R(m), exactly the specified effect for m occurred in that transaction; no effect of an admitted mutation becomes visible without its terminal receipt. A committed `conflict` R(m) changes no inspection. An aborted transaction exposes neither its provisional record effect nor provisional receipt claim. No incomplete claim is a terminal committed receipt.

**Scope/dependencies:** All API writes use the same PostgreSQL transaction/connection and constraints. Supports transaction aborts and application crashes; excludes out-of-band SQL writes and damaged storage. **Transitions/failure behavior:** Claim → adjudicate → record/terminal receipt → commit; faults before commit leave neither, faults after commit leave both. **Planned checks:** F1, F2, F6, F7, T-CONFLICT-REPLAY (Phase 1 onward). **Evidence boundary:** Actual PostgreSQL assertions at controlled boundaries are necessary; an in-memory transaction simulation cannot establish database atomicity, and transaction design alone cannot show the code uses it correctly.

### INV-IDEMP-01 — one immutable identity, one terminal outcome

**Statement:** Once R(m) exists, any valid submission with canonical bytes E(m) returns that same terminal outcome and causes no new effect. A different envelope using m returns identity collision and cannot alter R(m) or S. Concurrent same-ID contenders commit at most one receipt/effect. Retention bounds this claim to the lifetime of the unpruned database.

**Scope/dependencies:** Global unique key, ownership before record mutation, canonical byte comparison, no receipt pruning. Supports duplicates, concurrency, delayed replay and lost replies; excludes new IDs, deleted receipts or incompatible database replacement. **Transitions/failure behavior:** Duplicate waits on uncommitted claim, then replay/collision; aborted claim permits processing. **Planned checks:** F1, F2, F9, T-ID-COLLISION, T-CONFLICT-REPLAY, T-REPLAY-ADVANCED (Phases 1/3/5). **Evidence boundary:** Serial duplicates alone do not establish concurrent duplicate safety; replayed success alone does not establish stable conflict replay or collision rejection.

### INV-REV-01 — stale writes cannot replace newer records

**Statement:** Creation of a previously unused x yields revision 1. An admitted update/delete changes S(x) only when active and baseRevision equals its revision at adjudication, then advances exactly one. Among distinct mutations from the same base r, at most one can make the r→r+1 transition. No-change payloads still advance when accepted. Revisions never decrease or wrap.

**Scope/dependencies:** Record uniqueness, row locks and conditional predicate in the same transaction, server-owned positive BIGINT. Supports reordered and concurrent writers; excludes unconditional administrative writes. **Transitions/failure behavior:** Losers commit conflict receipts; overflow aborts without mutation success. **Planned checks:** F3, F7, F8, T-CREATE-RACE and T-REV-BOUNDS (Phase 1). **Evidence boundary:** A barrier-controlled database race supports this exact interleaving; two sequential requests do not establish race handling or arbitrary cross-record serializability.

### INV-DRAFT-01 — committed local intent survives supported restart

**Statement:** Once a local draft/freeze transaction completes, that committed intent remains recoverable under ordinary browser restart with the same profile until explicit user discard, acknowledged success, or explicit resolution transition archives it. Pull does not overwrite a pending proposal, base, or frozen envelope. Edits never committed locally are outside the claim.

**Scope/dependencies:** Correct multi-store IndexedDB transaction and retained persistent non-private profile. Supports browser process lifecycle and local transaction abort; excludes eviction, clearing, physical failure and unverified power-loss behavior. **Transitions/failure behavior:** Draft → queue atomically; a failed save leaves last committed draft and a visible unsaved error. **Planned checks:** F5, T-LOCAL-ABORT, T-PULL-PRESERVE (Phases 2/4). **Evidence boundary:** Actual process exit/relaunch and byte comparisons are required; page reload, mocked persistence, or virtual weeks do not prove process or long-duration physical durability.

### INV-ACKCLIENT-01 — local acknowledgment is atomic

**Statement:** For m, local terminal receipt installation, queue eligibility removal, active-work transition and clean-record handling form one transaction. After interruption, storage contains either the prior unresolved state or the complete terminal transition; it cannot forget m while omitting the receipt/conflict proposal. Historical replay cannot lower clean revision.

**Scope/dependencies:** IndexedDB transaction includes every affected store and UI success waits for completion. Supports process interruption/abort; excludes broken storage and nontransactional external UI persistence. **Transitions/failure behavior:** Response validated outside transaction; local abort leaves same-ID replay eligible. **Planned checks:** F1, F5, F9, T-LOCAL-ACK-CRASH (Phases 2/3/5). **Evidence boundary:** Crash/abort on both sides of actual commit supports this boundary; receiving a valid HTTP result does not prove local acknowledgment was durably recorded.

### INV-UNKNOWN-01 — ambiguity is resolved through original identity

**Statement:** If a transmitted m lacks a locally committed terminal receipt, the client retains E(m) and treats its outcome as unknown. No snapshot comparison, timeout, or retry budget exhaustion may turn it into a definitive conflict/rejection or authorize a replacement logical mutation. Recover/replay m before interpreting its effect; this includes resolution mutations.

**Scope/dependencies:** Persisted attempt-before-send marker, exact replay, server receipts. Supports lost reply, crash before/after send, late replies and advancing server revisions; excludes discarded local identity/storage. **Transitions/failure behavior:** Unknown remains locked through pull/retry failure; valid original success/conflict resolves it. **Planned checks:** F1, F6, F9, T-REPLAY-ADVANCED, T-ERROR-CLASSIFY (Phases 3/5). **Evidence boundary:** Need an intervening remote update to demonstrate that newer state is not misclassified; a lost response on an otherwise idle record tests less.

### INV-CONFLICT-01 — unresolved proposals remain explicit

**Statement:** A terminal conflict retains original base (when available), local proposal, original receipt/remote-at-decision, and a separate latest remote observation. It remains visible until an explicit keep-server confirmation or intentional resolution transition. New resolution envelopes use new IDs and latest observed bases; they may conflict again. Unknown resolutions obey INV-UNKNOWN-01.

**Scope/dependencies:** Local durable history, explicit user controls, revision validation. Supports racing resolutions and stale/deleted remote states; excludes user-confirmed discard and missing base for a new create. **Transitions/failure behavior:** Conflict → resolution draft → freeze → success/new conflict; no automatic field merge or drop. **Planned checks:** F7, F8, F9, F10, T-RESOLVE-RACE, T-DISCARD-CONFIRM (Phases 4/5). **Evidence boundary:** A single successful resolution does not establish second-conflict handling, non-discard behavior or lost-resolution recovery.

### INV-TOMB-01 — deletion cannot be silently undone

**Statement:** If S(x).deleted=true, later admitted mutations cannot make x active again. Its retained tombstone appears in complete snapshots. An exact repeated delete replays; a new delete ID on a tombstone conflicts without incrementing. Update of missing/deleted x never creates it.

**Scope/dependencies:** No physical deletion/pruning, server checks, snapshots include deleted rows. Supports old clients, stale updates, duplicate deletes and identity collisions; excludes administrative deletion of tombstones and explicitly created different IDs. **Transitions/failure behavior:** Active r → tombstone r+1; stale edits remain preserved conflicts. **Planned checks:** F10, T-TOMBSTONE, T-CREATE-RACE (Phases 1/4/5). **Evidence boundary:** Inspect both database and client; hiding deleted rows in UI alone proves neither retained tombstones nor prevention of resurrection.

### INV-SNAP-01 — coherent full reads and safe installation

**Statement:** Each accepted pull contains all server inspection rows from one query snapshot, including tombstones. Local installation is all-or-nothing and never overwrites work or decreases clean revisions; missing known authoritative IDs or equal-revision unequal state blocks installation. No partial response counts as complete.

**Scope/dependencies:** Single-query read, full-body validation, no stale HTTP caching, atomic IndexedDB write, serialized controller. Supports server writes concurrent with read, truncated responses and local abort; excludes a promise of present-time global equality or paginated mixed snapshots. **Transitions/failure behavior:** Failed validation/commit preserves prior complete state and work. **Planned checks:** T-SNAPSHOT, T-PULL-PRESERVE, F4, F10 (Phase 4). **Evidence boundary:** One GET on a quiet database is insufficient; controlled concurrent read/write and interrupted installation are needed. A valid snapshot may be old immediately after its query.

### INV-ONE-01 — one outstanding mutation per local record

**Statement:** For any c,x, count of active queued/unknown logical mutation IDs is at most one. The UI cannot edit/freeze another proposal for x until the prior terminal outcome is recorded and conflict handling explicitly permits a resolution draft. An acknowledged/conflict history entry is not active send eligibility.

**Scope/dependencies:** Transactional active slot and UI/controller checks, one controller per profile. Supports double-click/reentrant freeze attempts within that controller; excludes competing tabs as a supported usage mode. **Transitions/failure behavior:** Freeze rechecks draft version/slot; unknown remains locked; independent x values proceed. **Planned checks:** T-ONE-ACTIVE, F4, F9 (Phases 2/3/5). **Evidence boundary:** A disabled button alone is insufficient; inspect stored active IDs and rejected repeated freezes. This does not establish cross-tab arbitration.

### INV-RECON-01 — conditional eventual reconciliation

**Statement:** For a finite, eventually quiescent set of writes, if storage/databases work, receipts/tombstones remain, clients get repeated eventually reachable fair sync opportunities, blocked errors are repaired without losing identity, and users resolve all conflicts, each such client can eventually install the stable authoritative state and have no outstanding work. Without any condition, convergence is not promised.

**Scope/dependencies:** All previous invariants plus progress conditions; includes eventual recovery from temporary disconnection, not permanent partitions or endless new writes. **Transitions/failure behavior:** Recover → pull → push → pull; unresolved work prevents a synced label. **Planned checks:** F4, F8, F9, F10, T-SYNC-STATUS and DEMO-08 (Phases 4–7). **Evidence boundary:** A bounded successful scenario establishes an example under measured conditions, not a proof for every schedule or guaranteed instantaneous consistency.

## Deterministic harness architecture — full harness planned

Use a parent runner supervising a real local API subprocess, test-only HTTP gates, dedicated PostgreSQL database/schema, and persistent browser profiles launched by future browser automation. Pure state-machine simulations exercise scheduling cheaply but are reported separately from actual PostgreSQL, real IndexedDB, and lifecycle tests. An actual Node restart records exit, old/new PID and reuse of the same database. An actual browser restart records all test-browser process exits and relaunch of the same persistent profile, not merely a page reload or new context.

Named hooks: `after_local_draft_commit`, `after_local_freeze_commit`, `after_attempt_marker_commit`, `before_transport_send`, `before_server_admission`, `after_receipt_claim_before_record`, `before_record_lock`, `before_revision_adjudication`, `after_record_write_before_commit`, `after_commit_before_response`, `before_local_ack_transaction`, `after_local_ack_commit`, `after_snapshot_query`, and `before_snapshot_install`.
